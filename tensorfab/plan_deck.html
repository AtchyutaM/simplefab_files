Scheduling a semiconductor line

We are trying to learn a release-and-dispatch policy that decides, every tick, which tools to start — so that production tracks bursty demand without over-building or falling behind. This deck is the plan for making that problem progressively harder, in a controlled order, so we can find where each method breaks.

The decision

Each tick, for each tool: start a job or stay idle. A tool can only start if it is free and has enough input. Over a 4-week horizon that is 2,688 sequential decisions per tool.

The objective

Profit. Revenue on shipment, minus production cost, minus holding cost on finished goods and work-in-progress, minus backorder cost on late demand.

The tension

Build early and you pay to hold inventory. Build late and you pay backorder penalties. The batch tools take 16 ticks, so the pipeline must be filled well before demand lands.

Why this is worth the effort

A four-machine line is a toy. The real target has tens to hundreds of tools, multiple products sharing them, and reentrant flow — wafers revisiting the same tool many times. Exact optimisation is expected to become intractable there. The purpose of this programme is to find the crossover point: where the exact solver stops finishing, and whether a learned policy still works.

Naming caveat — please confirm

The code has no notion of "litho" or "diffusion". It knows only batch tools (4 units, 16 ticks) and single tools (1 unit, 2 ticks). Mapping batch → diffusion furnace and single → litho is a physical interpretation we have adopted, not something the simulator encodes. If you would map it differently, everything downstream renames but nothing breaks.

Recommended order

Run family 1 first — it needs no code changes and delivers four data points on the already-verified stack in an afternoon. Start the family 3 refactor in parallel, since generalising the machine count is also what family 5 needs. Family 2 last: it is the only one that introduces genuinely new physics.

Methods run in every cell

Commander heuristic · random search · hill-climb · gradient (straight-through) · Maskable PPO · CP-SAT with dual bound. Every profit figure is the schedule replayed through the exact integer simulator. CP-SAT solve time and remaining gap are recorded as first-class results — they are the scaling signal.

1c changes the objective, not just the difficulty

Line capacity is 672 units and raw material is 672 units, so 736 units of demand can never be met — at best 680 ship (672 produced + 8 initial stock). Profit will be strongly negative and every policy is really minimising backorder cost. That makes it a clean test of a different skill: triage rather than timing. Worth deciding explicitly whether raw material should also scale to 110%, so that machine capacity rather than material supply is the binding constraint — the two test different things and we should not conflate them.

Expected reading

From what we have already measured, the gradient's margin over zeroth-order search is large at 50% utilisation and small at ~90%. Family 1 tests whether that trend continues past 100%, where slack disappears entirely and there may be almost nothing left to optimise.

Family 2 — product mix

05 / 10

Two products sharing the same tools

What changes: every queue gains a product axis, tools gain a changeover state, and a batch becomes single-recipe. Held at 80% total utilisation so the mix — not the load — is the variable.

CellMixWhy it is interesting
2a50% A / 50% B Maximum changeover pressure; how often to switch is the whole problem
2b90% A / 10% B A dominates; when do you interrupt a good run for the rare product?
2cAlternating 90/10 ↔ 10/90 by week Mix itself is non-stationary — must anticipate the swing, not just react

Three genuinely new mechanics

  • Changeover. setup_times and setup_cost exist in config but are all zeros and unused. They have to become real, and a tool now carries state: which product it is configured for.
  • Per-product batching. A furnace batch is one recipe, so a tool can be starved on A while holding 3 units of B. That is new dynamics, not a bigger array.
  • Action space. Per tool becomes {idle, run A, run B} — MultiDiscrete([3,3,3,3]), and masking gets more involved.

This is where CP-SAT should start to hurt

Setup variables and sequence-dependent constraints are exactly what makes scheduling MILPs blow up. On the current four-machine, single-product problem CP-SAT already needs 600 s and still leaves a 0.4–1.5% gap. Family 2 is the first real test of the scaling premise — and the first place we should expect the learned methods to become genuinely competitive rather than merely close.

Family 3 — layers

06 / 10

Longer pipeline, one product — start here

What changes: the number of stages only. Same product, same costs, same demand. Each added diffusion+litho pair lengthens the pipeline by 18 ticks of unavoidable lead time.

3a  2 diff / 2 litho

Today's baseline. 36 ticks minimum flow time. Fully verified — the control.

3b  4 diff / 4 litho

The first build. 8 tools, 72 ticks minimum flow time. Doubles the decision dimension and the credit-assignment depth from release to revenue.

3c  6 diff / 6 litho

12 tools, 108 ticks minimum flow time. Becomes the platform for family 4.

Why this is the cheapest structural change

The tensor simulator already carries a machine axis on every array — q[B,M], reg[B,M,L], take, make. The only structural hardcoding is four lines of explicit routing. Replacing those with a route matrix generalises it to any serial depth, and the same route matrix is what family 5 needs for reentrancy. State grows linearly; no new physics.

Family 4 — compounding

07 / 10

6+6 tools, then re-run capacity and mix

What changes: nothing new — this is families 1 and 2 replayed on the deepest line. It answers whether difficulty compounds or saturates.

CellConfigurationQuestion it answers
4a6+6 × {50, 90, 110%, alt 80/110} Does a deeper pipeline make the capacity cliff sharper?
4b6+6 × {50/50, 90/10, alternating} Does changeover cost compound with pipeline depth?

The hypothesis worth pre-registering

A deeper pipeline means longer lead time, which means the build-ahead decision must be made even earlier relative to demand. If the gradient's advantage comes from long-range credit assignment, its margin should grow here while PPO's local reward gets relatively worse. If it does not, that weakens the mechanistic story considerably.

Where CP-SAT is most likely to fall over

12 tools × 2,688 ticks = 32,256 binary variables, three times today's model, plus setup variables in 4b. Record solve time and remaining gap at every cell — the shape of that curve is the single most important output of this whole programme.

Family 5 — reentrancy

08 / 10

Wafers revisiting the same tool

What changes: the routing map, and tools become shared across steps. This is the defining feature of real fabs and the primary source of scheduling difficulty — it couples early and late decisions on the same tool.

CellSharingWhat it isolates
5aBoth diffusion tools serve both diffusion steps; litho dedicated Contention on the batch bottleneck only
5bBoth litho tools serve both litho steps; diffusion dedicated Contention on the fast single-wafer tools only
5cFull reentrancy — any tool of a type serves any step of that type The real thing

The new decision

A shared tool must now choose which step to serve, not just whether to run. Serving a late step ships sooner; serving an early step keeps the pipeline fed. That is a genuine priority conflict with no local answer — exactly the kind of decision a horizon-aware method should win.

Cheap in tensors, expensive in MILP

In the tensor formulation reentrancy is just a richer routing map deciding which queue a completion deposits into — possibly the same tool's own input. The dynamics stay elementwise. In MILP the same sharing couples many binary start variables on one tool and is a principal driver of the explosion. This is the asymmetry the whole strategy rests on, and family 5 is where we finally measure it.

The headline metric

Not raw profit — that is not comparable across cells with different demand. Use % of the CP-SAT dual bound, which is a certified ceiling, and margin over the best zeroth-order method. Track CP-SAT solve time separately as the scaling signal; it is arguably the most important number in the whole programme.

The verification problem — decide this before writing code

The tensor simulator is currently trusted because it is checked tick-by-tick against an independent implementation, sim.py. Generalising only the tensor side loses that gate for any configuration other than 4 machines. Two options, and they are not equivalent:

  • Generalise sim.py too — keeps a true independent reference at every configuration. Slower, and doubles the refactor.
  • Regression + invariants — require the generalised code, configured as 4 machines, to reproduce today's verified results bit-exactly, then add property tests (unit conservation, no negative queues, tool never runs two jobs). Cheaper, but for 8 tools it is self-consistency, not independent confirmation.

Recommendation: do both, but stage them — regression plus invariants immediately so family 3 can start, and generalise sim.py before any result is published.

Sequence

  • Now: family 1 — config-only, runs on the verified stack today
  • Next: route matrix → 4+4 tools, with regression and invariant tests
  • Then: 6+6, and reuse the same route matrix for reentrancy (family 5)
  • Then: generalise optim.py — without a CP-SAT bound at 8 and 12 tools there is no ceiling to measure against, and the scaling curve is the deliverable
  • Last: the product axis and changeover (family 2), the only genuinely new physics
Open question before we start. At 110% utilisation, should raw material scale up too? As configured, arrivals are fixed at 672 units, so at 736 units of demand the line is starved of material as well as short of capacity — and the two failure modes get conflated. Scaling arrivals isolates machine capacity as the binding constraint. This needs a decision, and it also applies to every 110% cell in family 4.
